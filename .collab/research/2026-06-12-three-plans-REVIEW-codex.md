## A — Connect Metadata

**Verdict: MINOR-FIXES**

The first-review fixes are correctly folded at the design level. The old contradiction is gone: the plan now says `--no-metadata` must not suppress `cwd`, and `cwd` remains always captured while `metadata_opt_out` is just a consent flag. That matches the locked decision and the worktree guard: `check_worktree_mismatch` reads `reg.cwd` from the registry and skips only when it is `None` (`ocaml/c2c_broker.ml:1144-1153`), so keeping `cwd` unconditional is required. The CLI/MCP asymmetry is also real: CLI `register_cmd` currently calls `Broker.register` without `~cwd` (`ocaml/cli/c2c.ml:2901`), while the MCP handler passes `~cwd:(try Some (Sys.getcwd ()) ...)` (`ocaml/c2c_identity_handlers.ml:283-286`).

### Remaining Issue A1 — Record/signature file scope is incomplete

The plan says to add `metadata_opt_out : bool` to the registration record in `ocaml/c2c_broker.ml` and thread `Broker.register` there (plan lines 51-58). In the current source, the registration record is defined in **`ocaml/c2c_mcp_helpers.ml:1-76`** and exposed again in **`ocaml/c2c_mcp.mli:48-112`**. The exposed `Broker.register` signature is also in **`ocaml/c2c_mcp.mli:294`**.

If an implementer follows the plan literally and only edits `c2c_broker.ml`, the implementation and interface will diverge and the build will fail. The plan should explicitly add:

- `ocaml/c2c_mcp_helpers.ml`: add `metadata_opt_out : bool` to `type registration`.
- `ocaml/c2c_mcp.mli`: add the same field to the exposed `type registration`.
- `ocaml/c2c_mcp.mli`: add `?metadata_opt_out:bool` to `Broker.register`.

### Minor Notes

- The corrected state carry-over decision is sound: discard old `metadata_opt_out` on re-register, matching `_old_cwd` discard at `ocaml/c2c_broker.ml:1927` and new-record `cwd` assignment at `:1977`.
- The serialization plan is sound: omit false, read missing as false via the existing `bool_member_default` pattern (`ocaml/c2c_broker.ml:254-256`, `:272`).
- The test plan now includes the required guard invariant: `c2c register --no-metadata` still stores `cwd = Some _` (plan lines 69-76). Good.

**Safe to implement after minor file-scope fix:** yes.

## B — Name Hardening + Nonce

**Verdict: STILL-NEEDS-REWORK**

The first-review critical fix is partially folded: the plan now introduces `?from_auto_gen:false` and says blocklist enforcement applies only when `not from_auto_gen` (plan lines 23-48). It also correctly removes the MCP `no_nonce` argument (plan lines 64-69), seeds nonce generation defensively (lines 50-55), and adds the critical regression test that auto-generated client-prefixed names are not rejected (lines 84-90).

However, two important auto-gen paths are still broken or under-specified.

### Blocker B1 — Auto-gen origin is lost through install/start env auto-registration

The plan assumes auto-gen call sites can pass `~from_auto_gen:true` "when they register a generated name" (plan lines 39-45). That works for direct CLI registration sites such as `c2c init`, where an auto-generated alias is registered in-process at `ocaml/cli/c2c.ml:6758-6786`.

It does **not** work for the common install/start MCP path:

- `c2c install/setup` auto-generates an alias when `--alias` is omitted (`ocaml/cli/c2c_setup.ml:1522-1528`), then writes it into MCP config as `C2C_MCP_AUTO_REGISTER_ALIAS` for clients (`ocaml/cli/c2c_setup.ml:467`, `:581`, `:1051`, `:1384`).
- Managed `c2c start` also writes the effective alias into the child environment as `C2C_MCP_AUTO_REGISTER_ALIAS` (`ocaml/c2c_start.ml:2942-2949`; Kimi config path at `:3101-3122`).
- The MCP/server auto-register path later reads only that string (`ocaml/c2c_mcp_helpers_post_broker.ml:816-819`) and calls `Broker.register` without any origin flag (`:979`).
- The explicit MCP handler has the same shape: it falls back to `C2C_MCP_AUTO_REGISTER_ALIAS` (`ocaml/c2c_identity_handlers.ml:14-23`) and currently calls `Broker.register` without origin (`:283-286`).

So a default install alias such as `codex-ember-frost-a7c2` is generated by c2c, but by the time it reaches `Broker.register` it looks like a normal env-supplied alias. With the plan as written, the default `from_auto_gen=false` path will block it because first segment `codex` is banned. That is exactly the first-review critical bug, reintroduced across the config/env boundary.

The plan needs an explicit origin propagation design. One reasonable shape:

- When `c2c_setup.do_install_client` auto-picks the alias, write an internal env marker such as `C2C_MCP_AUTO_REGISTER_ALIAS_FROM_AUTO_GEN=1` alongside `C2C_MCP_AUTO_REGISTER_ALIAS`; do not write it when `--alias` was provided.
- When `c2c start` auto-picks `name`, propagate the same marker into `build_env`; do not set it for explicit `--name`, `--alias`, role alias, or user env.
- Teach `auto_register_startup` and the MCP register handler to pass `~from_auto_gen:true` only when that marker is present.
- Add tests for both sides: generated config/start aliases pass; user-provided env/explicit aliases like `codex` and `codex-code` still fail.

Without an origin marker or equivalent, `?from_auto_gen` is only reliable for direct in-process CLI registration, not for the main MCP auto-register surface.

### Blocker B2 — `--require-easy` can loop forever once nonce is appended

The plan says to apply the nonce inside the auto-generate functions before use/registration (plan lines 56-63). In `c2c init`, `--require-easy` validates the generated alias by splitting on hyphen and accepting only exactly two segments:

```ocaml
let w1, w2 = match String.split_on_char '-' a with [w1; w2] -> (w1, w2) | _ -> ("", "")
```

Source: `ocaml/cli/c2c.ml:6768-6776`.

After the plan changes `generate_alias_easy` to return `word-word-nn4x`, that split returns three segments, falls through to `("", "")`, fails the easy-pool check, and recurses forever. This is a concrete runtime blocker for `c2c init --require-easy` unless the plan changes one of:

- validate the bare easy-pool words before appending the nonce;
- make the `--require-easy` parser accept `[w1; w2; nonce]`;
- or thread a no-nonce path into this validation loop before adding the nonce.

Add an explicit test for `c2c init --require-easy` with nonce enabled so this cannot regress.

### Issue B3 — Plan example contradicts the locked blocklist rule

Plan lines 13-15 say blocklist checks full equality or first hyphen segment, then say it "allows `lyra-quill`, `claude-quill`." Under the stated rule, a **user-supplied** `claude-quill` has first segment `claude` and should be rejected. The tests later correctly include user-supplied `codex-code` rejection (plan lines 84-90), so this appears to be a stale example, but it is operationally confusing. Replace `claude-quill` with a non-banned first segment example.

### Minor Build-Scope Note

Just like Feature A, adding `?from_auto_gen` to `Broker.register` requires updating the exposed signature in `ocaml/c2c_mcp.mli:294`, not only `ocaml/c2c_broker.ml:1871`.

**Safe to implement as written:** no.

## C — Embed Client Plugins

**Verdict: MINOR-FIXES**

The first-review architectural fixes are correctly folded. The plan now:

- uses the correct `ocaml/c2c_start.ml:4629-4652` path instead of `ocaml/cli/c2c_start.ml` (plan lines 48-53);
- explicitly requires an `else` branch for the current silent no-op at `ocaml/c2c_start.ml:4637-4652` (plan lines 48-53);
- enumerates all four `just` recipes that need `codegen-opencode-plugin`: `build`, `build-cli`, `build-server`, and `install-all` (plan lines 36-38; current recipes at `justfile:140`, `:145`, `:150`, `:309`);
- keeps the hybrid model: dev checkout `data/opencode-plugin/c2c.ts` wins for symlink workflow, embedded content wins when the repo file is absent (plan lines 7-10, 41-53).

The current implementation evidence still matches the plan:

- `setup_opencode` depends on `data/opencode-plugin/c2c.ts` and reports "from c2c repo" when absent (`ocaml/cli/c2c_setup.ml:728`, `:760-786`, especially `:767-771`).
- `c2c start opencode` only writes the plugin when `plugin_src` exists and has no `else` (`ocaml/c2c_start.ml:4634-4652`).
- drift checker and doctor hint still contain repo-local repair wording (`ocaml/cli/c2c_opencode_plugin_drift.ml:146`, `:187`; `ocaml/cli/c2c.ml:2042`).

### Remaining Issue C1 — Byte-equality test path/wiring still under-specified

The glm51 review explicitly called out two test-specific details that are not folded into the hardened plan:

- The byte-equality test must resolve `data/opencode-plugin/c2c.ts` from the worktree root, not accidentally from Dune's test CWD. Prior review lines 178-180 called this out.
- If adding a new test file, the plan should include the Dune test stanza/module list. Prior review lines 180-182 called this out.

The current plan only says "extend `test_c2c_opencode_plugin_drift.ml` or add `test_c2c_opencode_plugin_embedded.ml`" (plan lines 55-59). That is probably enough for a careful implementer, but it is not a complete folded fix from the first review and can create a false start or false-green risk in the sync gate.

Recommended plan addition:

- If extending the existing drift test, reuse its canonical path resolution model deliberately.
- If adding `test_c2c_opencode_plugin_embedded.ml`, specify the `ocaml/cli/dune` test stanza and include `c2c_opencode_plugin_embedded` in that test's modules.

### Minor Note

The plan's "write embedded content by default" wording (lines 41-47) should keep saying dev checkout repo-file wins; otherwise an implementer might accidentally replace the symlink-tracks-edits workflow. The top-level decision lines 7-10 are correct, so this is only wording hygiene.

**Safe to implement after minor test-plan specificity fix:** yes.
