# B130 — c2c DM leaks into an unrelated dispatched subagent's transcript

- **Severity**: HIGH (cross-context isolation / privacy)
- **Status**: FIXED on `bl/B130-inbox-isolation` (commits 4f12380b, 61b8e067, 47130ec5)
- **Author**: subagent (B130 fixer), dispatched by coordinator

## Symptom

A coordinator Claude Code session ran `c2c init` (CLI-only, no MCP), alias
`claude-quip-neural-57cb`, with a persistent `c2c monitor`. A peer sent a DM to
that alias. The DM reached the coordinator (correct) AND the full DM body
surfaced inside an UNRELATED dispatched subagent (spawned via the Task tool for
a scoped git-wf2 task) that was never registered under the coordinator alias.

## Root cause (evidenced)

A dispatched Claude Code Task-tool subagent runs as a child process that
**inherits the parent session's env** — including `C2C_MCP_SESSION_ID` and the
session statefile pointer — and fires the **same c2c delivery hooks**
(PostToolUse / Stop / SessionStart). Those hooks resolve the inherited session
id, drain the owner inbox, and inject the DM as `additionalContext` into the
subagent's transcript.

The existing subagent guard `C2c_hook_lib.is_subagent_quiet` only recognised
`C2C_NO_AUTO_REGISTER=1`, which **nothing in c2c or the Claude Code harness ever
sets** for Task-tool subagents — so the guard never fired.

Direct evidence: env of a live dispatched subagent contains
`CLAUDE_CODE_CHILD_SESSION=1` (plus `CLAUDECODE=1`, `AI_AGENT=claude-code_..._agent`).
`CLAUDE_CODE_CHILD_SESSION` is the robust, harness-provided marker — set on every
dispatched child, never on a top-level session.

Reproduced at the unit level: `test_child_session_no_inbox_leak`
(`ocaml/cli/test_c2c_hook_claude.ml`) — with `CLAUDE_CODE_CHILD_SESSION=1` and an
inherited `C2C_MCP_SESSION_ID`, the SessionStart hook injected `secret coordinator
DM` + the owner's cold-boot context. Red before the fix, green after.

## Fix (c2c-side, env-gateable paths)

One canonical detector `C2c_mcp_helpers_post_broker.is_subagent_context ()`
(both signals: `C2C_NO_AUTO_REGISTER`, `CLAUDE_CODE_CHILD_SESSION`; fails toward
isolation). Every c2c-controlled entrypoint that runs **as its own child process**
now routes through it:

- All Claude/Codex/Grok hooks (`c2c_hook_cmd.ml`; the CLI-fallback Stop hook was
  previously unguarded), the standalone `c2c_inbox_hook` / `c2c_stop_hook`.
- The MCP auto-register path (`auto_register_impl`).
- The standalone context injectors `c2c_cold_boot_context.run` (was also
  consuming the owner's one-shot cold-boot marker) and `c2c_post_compact_hook_bin`.
- The CLI `c2c inbox`/`poll-inbox`/`wait-inbox`/`peek-inbox` on the IMPLICIT
  inherited-session path (explicit `--session-id`/`--alias` still allowed).

## NOT c2c-fixable via the env signal (harness boundary)

The following read an inbox keyed on the caller session but **cannot be gated by
`CLAUDE_CODE_CHILD_SESSION`**, because they execute in the **parent's** MCP server
process, not in the subagent's child process:

1. MCP `poll_inbox` / `peek_inbox` handlers (`c2c_inbox_handlers.ml`).
2. The inner MCP server watcher / channel auto-drain
   (`c2c_mcp_server_inner.ml`).

A Task-tool subagent **shares the parent's MCP server connection** — it does not
spawn its own server. The server resolves the session from its **own**
`C2C_MCP_SESSION_ID` (the parent's) and MCP carries **no per-RPC subagent
provenance**, so `is_subagent_context()` there reads the parent's env (never the
child marker) and would be a no-op. These are also the *explicit tool-call*
surface (the agent chooses to call `poll_inbox`), semantically distinct from
B130's *passive* leak.

Gating them would require Claude Code to pass subagent provenance in the MCP
request (it does not) or a per-subagent MCP session — a harness-side change, not a
c2c env-gate. Recommendation: track upstream; if/when Claude Code exposes
subagent identity to MCP tool calls or gives subagents their own MCP session, add
the gate then. Until then, do not add a no-op guard (false sense of security).

`c2c deliver watch` is intentionally not guarded: it REQUIRES an explicit
`--session-id` (never implicit inherited resolution), so it is not the
inherited-session leak, and guarding it would risk the managed-delivery sidecar.
